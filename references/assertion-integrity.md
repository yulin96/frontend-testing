# 断言强度与失败处理

## 先确定独立的预期

优先使用明确需求、协议/schema、已确认业务示例或需要保持的公共行为。既有测试也可能错误；当前实现、快照更新结果和 mock 默认值都不能单独定义契约。材料矛盾时指出矛盾，不选择最容易通过的解释。

每个关键测试应能回答：**哪一种错误实现会使它失败？** 如果空实现、错误身份、漏掉字段、重复调用或提前显示成功仍能通过，就补充与契约相关的断言。

| 契约 | 有效断言 | 会掩盖问题的改法 |
| --- | --- | --- |
| 返回指定用户的完整业务字段 | 断言用户 ID 和全部必需业务字段及值 | 只断言对象存在，或只检查任意一个字段 |
| 每次有效事件只上报一次 | 检查调用次数和每次关键参数，覆盖相同事件的重复投递 | 只检查“调用过”或把重复消息从样例中移除 |
| 失败时不覆盖旧文件 | 断言拒绝/错误内容、旧文件字节和未提交状态 | 只断言函数不抛错，或忽略错误后检查文件存在 |
| 列表按指定顺序且无重复 | 检查完整 ID 序列、数量和必要唯一性 | 对两边先排序、去重后比较，隐藏乱序和重复 |
| 数值允许指定精度误差 | 使用需求或算法误差界给出的容差 | 根据当前失败幅度不断放大容差 |
| CLI 用户可见文本一致 | 去掉 ANSI 控制码后仍精确比较业务文本 | 去掉标点、数字、行序等契约内容直到匹配 |

`toBeTruthy()` 可用于契约本来就是布尔真值的情况，但不能替代对象结构、状态码或数量断言。`objectContaining` 可忽略无关元数据，但必须覆盖本次行为依赖的全部字段。异常测试优先检查语义明确的类型、业务码或必要消息，不只断言任意异常。

## 失败后如何处理

1. 保留失败输出，复现同一命令、运行器版本和相关环境变量。检查测试是否确实执行，异步失败是否能传播到运行器。
2. 定位失败阶段：准备/导入、触发行为、结果断言或清理。环境错误不能作为回归测试“已证实缺陷”的红灯。
3. 按独立契约分类：
   - **实现缺陷**：保留失败断言。获得实现修复授权后修改根因；否则报告缺陷和复现。
   - **测试错误**：给出契约证据，修正输入、等待方式、隔离、mock 边界或预期，同时保留关键业务约束。
   - **环境/基础设施错误**：修复在授权范围内的运行入口、依赖解析或测试配置。不无依据地调整超时/并发、降低覆盖要求或关闭错误检查来掩盖原因；调整这些设置必须有诊断依据。
   - **契约不明**：列出会改变测试预期的最小业务问题，继续编写不依赖答案的测试。
4. 检查改动是否减少了关键条件、错误路径、调用次数约束或断言可达性。若因需求变化确实需要移除旧约束，明确说明新旧契约，而不是描述为“修到通过”。

## Mock 和回归证明

- Mock 应反映边界的真实协议：成功与失败形状、回调顺序、重试配置和异常传播。不能为了适配错误实现，让 mock 返回现实中不可能的状态。
- 导入真实被测模块；不要 mock 该模块再断言自己的 mock。测试跨模块行为时，保留参与该行为的内部模块，仅替换外部服务、时钟或设备边界。
- 不从被测函数计算 expected。使用小而可解释的固定例子或独立不变量。
- 回归修复需要证明目标测试在缺陷版本因目标行为失败、在修复后通过。可使用已有隔离 fixture 或临时副本，不破坏用户改动。
- 当新测试首次即通过且区分能力存疑时，可在隔离副本中做一次与风险对应的最小错误替换，确认断言能捕获；这不是每个任务的强制步骤，也不自动引入全量 mutation testing。
- 不批量接受快照更新。先解释每一类差异对应的预期行为，保留核心值与关键副作用的直接断言。
